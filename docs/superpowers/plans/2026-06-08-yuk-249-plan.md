## 1. 关键勘察结论（已亲自核实，load-bearing）

1. **graph 工具 domain 过滤已真实生效**（非偷懒只在 schema 必填）。`src/server/ai/tools/knowledge-readers.ts` L50-74 `loadKnowledgeRows(db, subjectId?)`：全量拉 `knowledge WHERE archived_at IS NULL`，in-memory 祖先 walk 算 `effectiveDomain`，`return rows.filter(row => effectiveDomain(row) === subjectId)`。`get_subject_graph_overview`（L296）与 `query_knowledge`（L412）均传 `input.subjectId` 进去。→ **§3 是核实 + 加回归测试，不是补实现**。

2. **seed 节点 ID 是不透明键，`wenyan` 子串纯属装饰**。`src/server/knowledge/seed.ts` L24 `seed:${curriculum.domain}:${seed.slug}` 是 ID 的**唯一构造点**；全仓 grep 确认 ID **从不被反向解析**提取 domain（无 `split('seed:')` / 无前缀解析）。→ **迁移可安全保留节点 ID 不变，只迁 `domain` 列值**，这是把 L 级 migration 风险从「高」降到「低」的关键（见决策点 D2）。

3. **`knowledge_edge` FK 无 `onUpdate: cascade`**（schema.ts L691-696）。若改 ID 会撞 FK；多张表把 knowledge_id 存成 jsonb 数组（L162/214/260/329/770 的 `knowledge_ids`、L806 view），改 ID 需级联重写所有这些站点。→ 进一步支持 D2「不改 ID」。

4. **skill 目录按 subjectId 解析**。`src/subjects/note-skills.ts` L37-42：`join(skillsRoot, subjectId, 'skills', 'note-<subjectId>', 'SKILL.md')`。`subjectId='yuwen'` 后会找 `src/subjects/yuwen/skills/note-yuwen/SKILL.md`。`quiz-gen-skills.ts` 同样按 `subjectId` 找父目录，但 `quiz-gen-<kind>` 目录名不含 subjectId。→ 父目录 `wenyan/` → `yuwen/` + 内层 `note-wenyan/` → `note-yuwen/`，`quiz-gen-*` 不改名（遵守 YUK-228 subject 后缀约定）。

5. **下一个 migration 序号 = 0029**（`drizzle/` 现到 0028）。migrate 命令 `drizzle-kit migrate`，`pnpm test:migration` 用独立 testcontainer 跑 DDL smoke。

6. **blast radius 计量**：107 个 `*.test.ts` 引用 `wenyan`，全仓 721 处 `wenyan` 字符串引用。多数是 test fixtures / test data。

## 2. 阶段一 — Domain 值迁移（migration + 数据回填）

### 2.1 设计决策（落地 D1/D2/D3，详见 §6）

- **迁的是值不是结构**：`UPDATE knowledge SET domain='yuwen' WHERE domain='wenyan'`。零 `parent_id` 改动、零边改动、零 ID 改动。完全合规钉板①②。
- **不改节点 ID**（D2 推荐 A）：`seed:wenyan:shici` 保持原样。ID 是不透明稳定键，无语义合同。规避 FK / jsonb 数组 / view 级联重写的高风险。
- **effective_domain 仍走查询期派生**（D3 推荐 A）：当前 root 节点 `domain` 设值、子节点 `null` 走祖先 walk 的设计不变。本 issue 不引入物化列（终版倾向派生；当前数据量祖先 walk 无性能问题，物化是过早优化）。

### 2.2 新建文件

| 文件 | 内容 |
|------|------|
| `drizzle/0029_wenyan_domain_to_yuwen.sql` | 见 §2.3 SQL |
| `drizzle/meta/_journal.json` + `drizzle/meta/0029_snapshot.json` | 由 `pnpm db:generate` 生成（**不要手写 journal**）。注意：本迁移是纯 data-only UPDATE，无 schema diff，drizzle-kit generate 不会自动产出 data migration——需手写 `.sql` 后手动追加 journal 条目，或用 `drizzle-kit generate --custom` 生成空壳再填 SQL。实施时优先 `--custom`，避免 journal 漂移。 |

### 2.3 Migration SQL（`drizzle/0029_wenyan_domain_to_yuwen.sql`）

```sql
-- YUK-249 — subject 顶层改名 wenyan → yuwen（domain 值迁移）
-- 钉板②：迁的是 root 节点的 domain 属性值；子节点 domain=null 不动，走祖先继承。
-- 钉板①：零 parent_id / 零 edge / 零 node-id 改动。
-- 节点 ID（seed:wenyan:*）保持不变——ID 是不透明稳定键，无语义合同（见 plan §1.2）。

-- 1) knowledge root 节点 domain 值
UPDATE "knowledge" SET "domain" = 'yuwen' WHERE "domain" = 'wenyan';

-- 2) learning_record 派生科目轴（nullable text，非结构列）
UPDATE "learning_record" SET "subject_id" = 'yuwen' WHERE "subject_id" = 'wenyan';

-- 3) memory_brief_note scope_key + subject_id
--    scope_key 有 unique 约束；'subject:yuwen' 行冲突时本迁移会失败 → 由前置 guard 检测（见 §2.4）
UPDATE "memory_brief_note"
  SET "subject_id" = 'yuwen', "scope_key" = 'subject:yuwen'
  WHERE "scope_key" = 'subject:wenyan';
```

**明确排除（不迁移，附理由注释）**：
- `event` 表 `subject_id`：`subject_kind='question'` 时是 question_id（entity 引用，不可变 audit trail）。
- `knowledge_mastery` / `material_fsrs`：`subject_kind + subject_id` 是 entity 引用（knowledge node id 等），不是 domain 轴。
- 所有 `knowledge_ids` jsonb 数组、`knowledge_edge` FK、view：因不改节点 ID 而无需触及。

### 2.4 前置 guard（migration 内或 scripts/migrate 前置检查）

`memory_brief_note.scope_key` unique 风险：若库里同时已有 `subject:wenyan` 和 `subject:yuwen` 行（冷启动一般不会，但需防御），UPDATE 撞 unique。处理：在 SQL 顶部加注释提示，并在 `pnpm test:migration` 新增一条 fixture 验证「单 `subject:wenyan` 行迁移成功」+ 一条「冲突场景预期失败」的断言（见 §5）。若 owner 要求生产零停机绝对安全，可改为 `INSERT ... ON CONFLICT DO NOTHING` 风格，但当前单用户工具无此需要——记为 D 决策附注。

### 2.5 原子性要求

migration SQL + 注册表代码改动（§3/§4）**必须同一 PR deploy**。否则注册表 `'yuwen'` 与 DB `domain='wenyan'` 脱节，`loadKnowledgeRows(db, 'yuwen')` 过滤返回空、`get_subject_graph_overview` 给空图。这是阶段一与阶段二/三必须同 PR 的硬约束。

### 3.3 seed 一致性说明（重要边界）

老库 root 节点 ID = `seed:wenyan:*`（迁移阶段一只改了它们的 `domain` 列值为 `yuwen`，ID 没变）。但改名后 `curriculum.domain='yuwen'`，`seedKnowledge` 会用新 ID `seed:yuwen:*` 去 by-id 查重，查不到 → 重复插入 7 个 root。

**解决（实施必做，否则生产重复种子）**：阶段一 migration **不改 seed 节点 ID**（保持 `seed:wenyan:*`），同时 **保留 `curriculum.json` 里 seed 节点的 ID 前缀稳定** 与 seed.ts 的 ID 构造解耦。最简方案：把 `seed.ts` L24 的 ID 构造从 `seed:${curriculum.domain}:${slug}` 改为**固定前缀** `seed:wenyan:${slug}`（或引入 `curriculum.seedIdPrefix` 字段，default `'wenyan'`，与 domain 解耦）。这样 domain 值迁到 yuwen，但 seed 节点 ID 仍 `seed:wenyan:*`，idempotent 查重命中、不重复插入。
- 记为 **决策点 D2c**：seed ID 前缀是否随 domain 改名（推荐**否**——保持 `seed:wenyan:*` 前缀稳定，解耦 ID 与 domain）。
- 测试断言更新：`seed.test.ts` 的 `expect(ids).toContain('seed:wenyan:shici')` 保持（不是改成 yuwen）；新增断言「seed 出来的节点 `domain === 'yuwen'`」。

## 6. Owner 决策点

- **D1 — migration 策略（DDL vs data-only）**：本 issue 是纯 data-only `UPDATE`（无 schema diff）。推荐 `drizzle-kit generate --custom` 产空壳 + 手填 SQL，避免手写 journal 漂移。owner 确认接受 custom data migration 形态。
- **D2 — 合成根命名**：subjectId 用 `yuwen`（拼音，与现有 math/physics 拼音风格一致）。
  - **D2a（id）**：`'wenyan'` → `'yuwen'`（推荐 yuwen，全英文/拼音 id 体系一致）。
  - **D2b（displayName）**：`'文言文'` → **`'语文'`**（扩科：语文 ⊃ 文言文，为后续现代文/作文留位）还是保 `'文言文'`？issue 标题写「文言文(wenyan) → 语文(yuwen)」，倾向 `语文`。**待 owner 拍板**。
  - **D2c（seed ID 前缀）**：保持 `seed:wenyan:*` 前缀稳定（推荐，解耦 ID 与 domain，规避 FK/jsonb/view 级联），还是连 ID 一起迁 `seed:yuwen:*`（高风险，需级联重写所有引用站点）？**强烈推荐保持 `seed:wenyan:*`**。
- **D3 — effective_domain 派生方式**：查询期祖先 walk（现状，推荐保留——当前数据量无性能问题，终版倾向派生）vs 物化 domain 列（过早优化）。推荐**维持查询期派生**。
- **D4 — memory_brief_note scope_key 冲突处理**：撞 unique 时让迁移 fail-loud（推荐，单用户工具冷启动不会撞）vs `ON CONFLICT DO NOTHING` 兜底。推荐 fail-loud + migration 测试覆盖冲突场景。
