## 2. 数据流 / 接口变更

### 公开签名变更（4 个导出函数）

```
resolveNoteSkill(subjectId, skillsRoot?)              : string[] | undefined
  → async resolveNoteSkill(...)                       : Promise<string[] | undefined>

resolveQuizGenSkills(subjectId, kind, skillsRoot?)    : string[] | undefined
  → async resolveQuizGenSkills(...)                   : Promise<string[] | undefined>

resolveQuizGenSkillsForSubject(subjectId, skillsRoot?): string[] | undefined
  → async resolveQuizGenSkillsForSubject(...)         : Promise<string[] | undefined>
```

返回值语义、降级链行为（缺 SKILL.md → `undefined`）、缝隙防御（note 不返 quiz-gen-*、反之亦然）全部不变。仅时序从同步变异步。

### `existsSync → fs.promises.access` 错误语义

`access` 在文件不存在时 throw `ENOENT`（非返回 bool）。标准替换模式：

```ts
import { access, readdir } from 'node:fs/promises';
// ...
try {
  await access(skillFile);
} catch {
  return undefined;
}
return [noteSkillDir];
```

每个替换点的 catch 分支必须返回 `undefined`，**不得 re-throw**——这等价于原 `if (!existsSync(...)) return undefined`。

`resolveQuizGenSkillsForSubject` 的 `readdirSync` → `await readdir(..., { withFileTypes: true })`，已在的 try/catch 块（行 92-99）外层结构保持，但因为 filter 内还有一处 `existsSync`（行 95），改造时该 filter 也需异步化（见 §3 第 3 点）。

### 调用方上下文

所有 5 个调用方已在 `async function` 体内，加 `await` 零结构成本。仅两处需结构调整（§3）。

## 3. 三处需结构调整的调用点（唯一非平凡部分）

### 3.1 `quiz_gen.ts:453-455` — `Array.filter` 异步谓词

现状（同步谓词，改 async 后 `resolveQuizGenSkills` 返回 Promise，`!== undefined` 恒为 true，会静默 bug）：

```ts
const skillBackedKinds = (subjectProfile.questionKinds ?? []).filter(
  (k) => resolveQuizGenSkills(subjectProfile.id, k) !== undefined,
);
```

改为 `Promise.all` 预计算 bool 再 filter：

```ts
const allKinds = subjectProfile.questionKinds ?? [];
const skillResolved = await Promise.all(
  allKinds.map((k) => resolveQuizGenSkills(subjectProfile.id, k)),
);
const skillBackedKinds = allKinds.filter((_, i) => skillResolved[i] !== undefined);
```

这是 issue 风险点 4 / 勘察风险点 4 标注的「唯一结构性变更」。**必须**这样处理，直接对异步谓词用 `Array.filter` 是 bug。

### 3.2 `quiz_gen.ts:446` — 简单 await

```ts
const subjectSkills = await resolveQuizGenSkillsForSubject(subjectProfile.id);
```

### 3.3 `quiz_verify.ts:291-293` — 条件 ternary

现状：

```ts
const verifySkills = kindConformanceChecked
  ? resolveQuizGenSkills(subjectProfile.id, row.kind as SubjectQuestionKind)
  : undefined;
```

`resolveQuizGenSkills` 改 async 后，true 分支是 Promise、false 分支是 `undefined`，类型变成 `Promise<...> | undefined`。需统一 await：

```ts
const verifySkills = kindConformanceChecked
  ? await resolveQuizGenSkills(subjectProfile.id, row.kind as SubjectQuestionKind)
  : undefined;
```

`await` 只在 true 分支求值（短路保留），false 分支仍同步给 `undefined`。`verifySkills` 类型回到 `string[] | undefined`，下游用法不变。

## 6. 风险点

1. **filter 异步谓词（quiz_gen.ts:454）**——最高风险。改 async 后 `resolveQuizGenSkills(...)` 返回 Promise（truthy），`!== undefined` 恒 true，所有 kind 都被当作 skill-backed，静默错。**必须**用 §3.1 的 `Promise.all` 预计算 bool。tsc 不一定能抓（Promise `!== undefined` 是合法表达式），靠 §3.1 改法 + 单测/handler 测试兜底。这是本次唯一会引入语义错误的点。

2. **handler 测试靠 live SoT fs（非 mock）**——风险低。三个 note handler 测试断言依赖真实 `src/subjects/<id>/skills/note-<id>/SKILL.md` 存在；await 改造后 `ctx.skills` 赋值时序不变。若意外失败说明 await 链接错，回查 handler 而非改测试。

3. **`fs.access` 错误语义与 `existsSync` 不同**——`access` 文件不存在 throw `ENOENT`，必须 try/catch 返回 `undefined`、绝不 re-throw。每个替换点都要核 catch 分支。

4. **中间态 tsc 失败**——resolver 改 async 而调用方未加 await 时，Promise 赋给 `string[]` 槽，tsc 报错。靠 §5 commit 切分（resolver + 调用方同 commit）规避。

5. **`fs.promises.access` 全仓首例**——代码库无既有 `fs.promises.access` 用例，本次是第一处。模式本身是标准 Node.js，无新依赖，无风险；只是 reviewer 会注意到是新模式。
