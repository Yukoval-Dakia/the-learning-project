## 0. Scope 定义（owner 约束硬性）

把 agent-notes 从「quiz_verify 唯一 writer」扩成多个 narrow task writer，并把 `copilot` 加入 target vocab。**不强行 MCP 化**——`notes.ts` 顶部注释明确 `MCP DomainTool WRAPPER IS DEFERRED (YAGNI)`，本 issue 核实哪些 task 真有 note 可留 + 接线确定性写端，MCP wrapper 仅在确证有 tool-loop 消费者时才做（见 §6 owner 决策点）。

现状（已勘察确认）：
- `src/server/agents/notes.ts`：`writeAgentNote` / `readAgentNotes` service 函数稳定，code-invoked，零 schema 变更（`experimental:agent_note` event）。`AgentNoteTarget = 'dreaming' | 'maintenance' | 'coach'`，**缺 `'copilot'`**。
- 唯一 writer：`quiz_verify`（参考先例：txn 提交后 fire-and-log，try/catch 只 console.error，带 caused_by + 30天 expires_at）。
- readers：`dreaming_nightly`(for_agent='dreaming')、`coach_daily`('coach')、`knowledge/review`('maintenance')。**copilot 无 reader**。
- copilot agent runner：`src/server/copilot/chat.ts`，经 `resolveMcpAllowedTools('copilot')` + `buildMcpServerFromRegistry` 挂 loom MCP——这是 MCP 路径与 copilot 注入的唯一 attach 点。

### 0.1 In-scope（本 lane 必做）

确定性写端（code-invoked，**不碰 prompt / allowlist**，可独立先行，不受 YUK-284 阻塞）：

1. **`sourcing`**（`runSourcing` success 路径）：whitelist_match=false 的源批量写入 → `signal_kind='source_quality_low'`，target `['coach']`。**最干净的写端**——已有 `db` / `triggerEventId` / `taskResult.task_run_id`，模式与 quiz_verify 1:1。
2. **`tagging`**（`runTaggingTask` 返回后）：suggestions 为空 / 全被 anti-hallucination filter 过滤 → `signal_kind='tagging_gap'`（建议复用既有 `coverage_thin` 词，见 §6 决策），target `['dreaming']`。caused_by 降级见 §5 风险1。
3. **`block-assembly`**（`runBlockAssemblyForSession` 检测到 candidates）：反复切断模式 → `signal_kind='block_split_pattern'`，target `['dreaming']`。同样 caused_by 降级。

target vocab：

4. **`AgentNoteTarget` 加 `'copilot'`** + 更新 `notes.ts` 顶部 DEFERRED 注释（标注 copilot 已纳入 vocab，MCP wrapper 仍 deferred 直到有 tool-loop 消费者）。

### 0.2 Deferred / out-of-scope（本 lane 明确不做，理由记录）

- **MCP `write_agent_note` / `read_agent_notes` DomainTool**：owner 约束「不强行 MCP 化」。加 `'copilot'` 到 vocab 后，**copilot 目前没有任何 reader 消费 for_agent='copilot' 的 note**（勘察确认）。在没有消费者前，MCP writer 会写出 dead notes。MCP 化 + copilot reader 注入 + systemPrompt 准则一并 **defer 到 YUK-284 merge 之后**（YUK-284 同碰 copilot allowlist / systemPrompt 结构）。本 lane 只把 `'copilot'` 加进 type union，让 vocab 就位；不接 MCP，不动 `allowlists.ts`，不动 copilot prompt。详见 §6 owner 决策点 D1/D3。
- **copilot 作为 writer**（对话 agent 发现用户系统性误解 → 留 hint）：这是 MCP 路径（模型 mid-loop 调 `write_agent_note`），与上同 defer。
- **judge 链连续误判 writer**：需跨 run 累计统计，单次 judge 无法判「连续」，无统一入口。scope 最大，**defer**，不在本 lane。
- **seam 扩展暴露 task_run_id**（`TaggingRunTaskFn` / `BlockAssemblyRunTaskFn` 返回 `{ text }`）：breaking change for injected stubs，本 lane 接受 `caused_by=null` 降级，seam 扩展另起 follow-up（见 §7 Linear gate）。

## 2. 数据流 / 接口变更

- **零 schema 变更**：所有 note 仍走 `experimental:agent_note` ExperimentalEvent escape hatch。
- **`AgentNoteTarget` type union 扩展**：`'dreaming' | 'maintenance' | 'coach' | 'copilot'`。这是唯一对外接口变更。下游 `readAgentNotes` 的 `for_agent` / `ReadAgentNotesOpts` 自动接受新值，无需改 `readAgentNotes` 实现（jsonb containment 已泛化）。
- **新增 signal_kind 字面量**（自由字符串，无 schema 约束）：`source_quality_low`、`tagging_gap`（或复用 `coverage_thin`，见 §6 D2）、`block_split_pattern`。YUK-294 留言板 UI 已有 unknown-kind fallback（#358），新 kind 直接渲染，**UI 零改动**。
- **caused_by 链**：sourcing 写端有完整 evidence chain（triggerEventId + task_run_id）；tagging / block-assembly 因 seam 限制写 `caused_by_event_id=null`（降级，非回归——note 仍带 source_task_kind + refs 提供 provenance）。
- **writer invariant**（所有新写端共用，复刻 quiz_verify 先例）：
  1. 在已提交事务**之外**调用（note 绝不引用被回滚的 event）；
  2. try/catch 包裹，catch 仅 `console.error`（non-fatal，绝不影响主流程）；
  3. 带 refs（knowledge_ids 优先，回退到 question/block id）+ expires_at（30天软过期）。

## 5. 风险点

1. **tagging / block-assembly seam 不暴露 task_run_id**（`TaggingRunTaskFn` / `BlockAssemblyRunTaskFn` 返回 `{ text }`）。→ 接受 `caused_by_event_id=null` 降级（note 仍带 source_task_kind + refs，evidence 不为零）。扩 seam 是 breaking change for injected stubs，另开 follow-up（§7）。**不**在本 lane 改 seam。
2. **block-assembly note 位置**：必须在 `db.transaction` 之外、且在 §3「BlockAssemblyTaskError 被上层 swallow」的 best-effort 区域写。candidates 来自 `output.candidates`，在 task 成功返回后才有——放在 `runBlockAssemblyTask` 返回后、写 proposal 的同一 best-effort 段。AI 失败时无 candidates，自然不写 note，符合预期。
3. **sourcing note 不计入 proposal cap**：sourcing 不走 dreaming/coach 的 `beforeExecute` proposal-cap 路径（那是 MCP tool-loop 的事），`writeAgentNote` 是 code-invoked service 调用，**不经 mcp-bridge**，不会被 `effect==='propose'|'write'` 计数截断。本 lane 全是 code-invoked，§5 勘察风险3（MCP effect 归类）**不适用**——它只在 MCP 化时才相关。
4. **copilot vocab 加入后无消费者**：加 `'copilot'` 到 union 让 vocab 就位，但**本 lane 不产生任何 target=['copilot'] 的 note**（写端都 target dreaming/coach），所以不会写出 dead notes。真正产生 copilot note 的 MCP writer + copilot reader 一并 defer（§0.2）。这是有意的——vocab 先行、消费者随 YUK-284。
5. **best-effort 不回归主流程**：所有写端必须复刻 quiz_verify 的 fire-and-log，单测显式验证「note-write throw → 主任务仍成功」（§3）。这是最易写错的点（漏 try/catch 会让 note 失败炸掉录入 / sourcing）。

## 6. owner 决策点（需 owner 拍）

- **D1 — MCP wrapper 做不做？**（owner 提示原文：notes.ts 注释说 defer 到 tool-loop agent 真需要时）
  本 plan **默认 D1=defer**：copilot 目前无 reader 消费 for_agent='copilot' 的 note，MCP writer 会写 dead notes；且 MCP 化触及 copilot allowlist / systemPrompt，被 YUK-284 阻塞。建议 vocab 先行、MCP 随 YUK-284 一并做。若 owner 要本 lane 就做 MCP，则需先确认 copilot reader 注入点（chat.ts）也同批落地，否则 note 无人读。
- **D2 — tagging 用新 `tagging_gap` 还是复用既有 `coverage_thin`？**
  既有 signal_kind 词表已有 `coverage_thin`（测试中出现）。复用保持 vocab 收敛、UI 分类一致；新造 `tagging_gap` 语义更精确但扩词表。建议复用 `coverage_thin`（§4.1 vocab 共享原则），owner 确认。
- **D3 — copilot reader 消费方放哪？**（owner 提示：target vocab copilot 加入后 readAgentNotes for_agent 消费方在哪）
  唯一候选是 `src/server/copilot/chat.ts`（runCopilotChat 组 prompt 时注入，mirror dreaming/coach 的 readAgentNotesFn DepsOverride 缝）。本 plan 把它 defer 到 YUK-284 之后（同碰 prompt 结构）。owner 确认是否接受「vocab 先行、reader 随 YUK-284」，还是要本 lane 一并接 reader。
- **D4 — 写端优先级**（owner 提示：哪些 task 优先成 writer，copilot 误解检测最有价值？）
  copilot 误解检测是 MCP 路径（模型主观判断），落在 D1 defer 范围。本 lane 确定性写端按「干净度」排序优先 sourcing > tagging > block-assembly（sourcing 有完整 evidence chain，零 seam 改动）。owner 若认为某个确定性写端无实际价值可砍。
