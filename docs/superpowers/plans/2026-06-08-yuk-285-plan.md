## 1. 现状 → 目标（数据流变更）

### 现状（origin/main，teaching = 短路 one-shot）
```
POST /api/copilot/chat { skill_context:{skill:'teaching', ref:{kind,id}} }
  → runCopilotChatImpl 短路分支 (req.skill_context.skill==='teaching')
  → runTeachingSkill() → run('TeachingTurnTask', {messages:[单条 user]}, {allowedTools:[]})  // maxTurns:1, 无 loop, 无 history
  → parseTurnOutput → {kind: explain|ask_check|end, structured_question?}
  → db.transaction: materializeAskCheckQuestion + write copilot_reply event (skill_turn 持久化)
  → 返回 skill_turn
```
节奏（explain→ask_check→end）由 `buildTeachingTurnPrompt`（task-prompts.ts）内隐式概率控制；判分无连贯触发（每 turn 独立）。

### 目标（YUK-285，teaching = loop + 显式状态）
```
POST /api/copilot/chat { skill_context:{skill:'teaching', ref}, ... }
  → free-form CopilotTask loop（不再短路；teaching 是 loop 的一个 skill-flavored 变体）
  → 注入: teaching SKILL.md + conversation_history + teaching_context（learning_item/artifact/parent_hub）
  → allowedTools = copilot read tools + set_teaching_state (+ materialize_question, 见 OWNER DECISION 2)
  → 模型 loop:
      set_teaching_state({phase})          // 每轮必调一次（合同）
      [phase=awaiting_answer 时] 出题 → (materialize question, 见 OWNER DECISION 2)
      回复正文
  → loop 结束: chat.ts 从 set_teaching_state 工具调用读出 final phase → 写进 copilot_reply payload.teaching_phase
  → 返回 reply + teaching_phase (+ structured_question)
```
下一轮用户提交时：
```
chat.ts 读「上一条 copilot_reply.teaching_phase」 + getActiveQuestionState(db, sessionId)
  ├─ phase==='awaiting_answer' && active_question_id 非空
  │     → 用户这条提交 = 答题 → 路由到判分（POST embedded-check/attempt 语义）→ materialize attempt
  │     → 判分结果回流进 teaching loop 作为下一轮 context（讲评）
  └─ phase==='digression'（或 explaining/idle）
        → 用户这条提交 = 题外话/继续对话 → 不判分 → 正常进 teaching loop
```

## 3. 状态持久化方式（推荐 = 方案 A，待 OWNER DECISION）

**推荐：方案 A — `teaching_phase` 落 `copilot_reply` event payload**（evidence-first，零 migration）。

- 每轮 reply event payload 加一个 string 字段 `teaching_phase: 'teaching_idle'|'explaining'|'awaiting_answer'|'digression'`。
- 「当前态」= 最新一条 `copilot_reply` event 的 `teaching_phase`。读法复用 `getRecentCopilotTurns` / 已有的 session-scoped event 查询。
- 与 `skill_turn` / `skill_context` 同层级（都已在 payload，turns.ts 已有解析样板）。
- 与 ADR-0006 event-sourcing 对齐：状态轨迹是事件历史的自然投影，可回放可审计可回滚。
- **不新增表、不新增列、不新增 migration**（不触发 `pnpm audit:schema` 漂移）。

备选见 §6 ADR，owner 拍。

## 4. 风险点（含勘察报告 R1–R6 的处置）

- **R5（最大架构风险，judged 已半解）— ask_check 物化的原子性 in loop**。现状 ask_check 在 chat.ts `db.transaction()` 内与 reply event 原子化（PR #305）。改成 loop 后若让模型用 `materialize_question` 工具，SDK 在 loop 内**异步**调它，**无法纳入 chat.ts 外层 tx**。
  - **推荐处置（OWNER DECISION 2 = A）**：**不把 question 物化做成工具**。模型用 `set_teaching_state({phase:'awaiting_answer'})` + 在回复正文/结构化字段里给出题目，chat.ts 在 **loop 结束后**于单个 `db.transaction()` 内 materialize question + 写 reply event（**完全保留 PR #305 原子性**）。题目结构从模型输出解析（沿用 `TeachingStructuredQuestion` schema / `parseTurnOutput` 的 structured_question 片段）。即：状态用工具显式写，**物化仍由 chat.ts 在 tx 内做**，工具只负责「声明状态」不负责「写 question 行」。
  - 备选 B（工具内物化 + 后置提交）复杂且破坏原子性，不推荐。owner 拍。
- **R1 — 判分触发的 race**。loop 内模型可能连出两题。`getActiveQuestionState` 已是 `ORDER BY created_at DESC, id DESC LIMIT 1`（active-question.ts:73）= 最新 teaching_check question 即 active，语义已对。**eval 必须覆盖**「连续两轮 awaiting_answer，第二题覆盖第一题为 active；用户提交判到最新题」。
- **R2/R4/R6 → 转 OWNER DECISION + eval**：set_teaching_state 是否入 COPILOT_TOOLS（D4）；digression 误判隔离（模型误把含答案的题外话标 digression 致漏判，反之亦然）靠 SKILL.md 红线 + eval 断言「该判分时判分/digression 不判分」；activeSkillRef 简化随 loop 生命周期对齐（end 清）。
- **R3 — TeachingTurnTask 退役的 eval 回归**：`TeachingTurnOutput` schema + `parseTurnOutput` **保留**（loop 内解析模型出题片段仍用它；也作 eval 对比基线）。task 本身可标退役但解析契约不删。
- **R（新）— 判分回流**：判分结果（outcome/feedback）要回流进 teaching loop 下一轮做讲评。机制：判分后写的 attempt event 在同一 session 内，loop 的 `conversation_history` / teaching context 读到它即可（或 chat.ts 在判分后把 judge 摘要塞进下一轮 run input）。**需 eval 覆盖**「答错 → 下一轮模型讲评 + 可回 explaining」。
- **R（新）— digression → awaiting_answer 回转条件**（OWNER DECISION 3 关联）：digression 答完旁支后**自动回 awaiting_answer**（题还挂着没清）。由模型下一轮 `set_teaching_state` 重新声明，还是 chat.ts 在「上轮 digression 且 active question 仍在」时强制视为 awaiting_answer？推荐**模型声明为准 + chat.ts 用 active-question 兜底**（active question 还在 = 题没答完，digression 只是插曲）。owner 拍。

## 6. ADR 草案（Commit 1 内容 — owner 拍前不实施 §2 之后）

> 文件：`docs/adr/00XX-teaching-state-machine.md`。**号待定**：实施 lane `ls docs/adr/ | sort` 取下一个空号（勿硬编码，仓库有别的 bot 在开 ADR）。

### ADR 标题：Teaching loop 状态机 + set_teaching_state 显式状态写

#### Context
现状 teaching 是 one-shot service call（TeachingTurnTask, maxTurns:1，无 history，无 loop），节奏靠 prompt 隐式概率控制，判分无连贯触发。owner 决定：teaching 进 loop（吃 conversation_history），但模型必须**显式写状态**而非隐式控节奏，以便 eval 可断言、判分有确定触发判据。

#### Decision：四态状态机

```
          ┌──────────────┐
          │ teaching_idle │  (session 开始前 / end 后静止)
          └──────┬───────┘
                 │ 用户开始教学 turn
                 ▼
          ┌──────────────┐  讲解递进
   ┌─────▶│  explaining   │◀────────┐
   │      └──────┬───────┘          │
   │ 答完讲评      │ 出题(出 ask_check) │ 答完/讲评结束
   │ 回到讲解      ▼                   │
   │      ┌────────────────┐         │
   │      │ awaiting_answer │─────────┘
   │      └───┬────────┬───┘
   │  判分(答题)│        │ 用户问题外话
   │          │        ▼
   │          │   ┌────────────┐
   │          │   │ digression  │ (答旁支, 不清题, 不判分)
   │          │   └─────┬──────┘
   │          │         │ 旁支答完, active question 仍在
   │          │         └──────▶ 回 awaiting_answer
   │          ▼
   └──── 判分后讲评 → explaining (或再出题 → awaiting_answer, 或 end → teaching_idle)
```

转移规则：
- `teaching_idle → explaining`：进入 teaching turn。
- `explaining → awaiting_answer`：模型出 ask_check（`set_teaching_state({phase:'awaiting_answer', question_id})`）。
- `awaiting_answer → (判分) → explaining`：用户提交被判分，判分结果回流，模型讲评。
- `awaiting_answer → digression`：用户提交题外话，模型识别并 `set_teaching_state({phase:'digression'})`，**不清 active question，不判分**。
- `digression → awaiting_answer`：旁支答完且 active question 仍在 → 模型重新声明 awaiting_answer（chat.ts 用 active-question 兜底）。
- `* → teaching_idle`：模型判定教学结束（end），清 active context。

#### set_teaching_state tool 合同
```ts
// 工具名: set_teaching_state
// 语义: 模型每轮显式声明「这一轮结束后教学处于什么态」。每轮 SHOULD 调一次（合同；
//       未调 → chat.ts 沿用上一轮 phase 兜底 + eval 记一次 soft-fail，不硬崩）。
// 输入:
//   { phase: 'teaching_idle' | 'explaining' | 'awaiting_answer' | 'digression',
//     question_id?: string }   // 仅 phase==='awaiting_answer' 时指向当前 active question
// 返回: { ok: true, phase }    // 纯确认；不写 question 行（物化由 chat.ts 在 tx 内做, R5）
// effect: 'write'（写状态语义；实际 question/event 物化在 chat.ts）
// mirrorEvent: 'when_user_visible'（teaching 是 user-visible turn）
```

#### 判分触发判据（确定性，不靠模型「假装判分」）
用户**下一条**提交进 chat.ts 时：
1. 读「上一条 copilot_reply event 的 `teaching_phase`」。
2. `getActiveQuestionState(db, sessionId)` 取 active_question_id。
3. **判分当且仅当** `teaching_phase==='awaiting_answer'` **且** `active_question_id !== null`。
4. 命中 → 这条提交路由到判分（embedded-check/attempt 语义：judge teaching_check question → 写 attempt event →(failure)建 record+attribution）→ 判分结果回流 loop 讲评。
5. 不命中（含 digression/explaining/idle）→ 这条提交正常进 teaching loop，不判分。

#### 状态持久化方案（含 ≥2 备选对比 + 推荐）

| 方案 | 机制 | 优点 | 缺点 | 裁决 |
|---|---|---|---|---|
| **A（推荐）event payload** | `teaching_phase` 落每条 `copilot_reply` payload；最新 event 即当前态 | 零 migration；与 skill_turn/skill_context 同层级（已有解析样板）；evidence-first，轨迹可回放（ADR-0006）；不触发 audit:schema | 每次取当前态要查最新 event（已有 session-scoped 查询，成本低） | **推荐** |
| B `learning_session.metadata` jsonb | 每轮 UPDATE session.metadata.teaching_phase | 一次 SELECT 即得当前态 | 每轮多一次 UPDATE；丢失历史轨迹；与 event-sourcing 原则相悖；写 path 要过 audit:schema | 否 |
| C 专用 `teaching_state` event action | 独立 `experimental:teaching_state` event | 状态与 reply 解耦，纯状态流 | 多一类 event；与 reply 强绑定的态被拆开两条 event 反而难对齐；replay 要 join | 否（A 已够，无第二实例需求触发抽象） |

#### set_teaching_state：tool vs 结构化输出字段（OWNER DECISION 1）

| 选项 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **tool（倾向推荐）** | DomainTool，模型显式 call | 与现有 tool-loop 一致；eval 可断言「调没调/调了什么」；tool_call_log 留痕；与 YUK-293 agent-note 写工具方向一致 | 多一个 tool 进 allowlist（D4 张力）；占 iteration 预算 |
| 结构化字段 | 模型在最终 JSON 输出里带 `teaching_phase` | 不占 tool 预算；不动 allowlist | free-form CopilotTask 是**文本流式**输出（YUK-266），没有强制结构化 JSON schema；要么破坏 streaming，要么靠尾部解析（脆）；eval 难断言中间态 | 

> 推荐 tool：free-form 路径已是 streaming 文本，塞结构化输出字段会与流式回复打架；tool 调用是 loop 内的自然中间动作，且天然留痕（tool_call_log + mirror event）。但这是 ADR 级 owner 决策。

#### 备选总览（one-shot vs loop+显式状态）

| 维度 | 当前 one-shot | loop + 显式状态（本 ADR）|
|---|---|---|
| 历史上下文 | 单条 user message，无历史 | conversation_history（YUK-267 已建）|
| 节奏控制 | prompt 内隐式概率 | set_teaching_state 显式（可 eval 断言）|
| 判分触发 | 无连贯触发 | awaiting_answer + active question 确定触发 |
| digression | 无（每轮独立）| 显式标记，不判分，答完回 awaiting_answer |
| 原子性 | db.transaction 已保证 | **保持**（物化仍在 chat.ts tx 内，R5 处置 A）|
| 流式 | one-shot 推一条 | 继承 free-form streaming（YUK-266）|

### db（`vitest.db.config.ts`，shared testcontainer）

  - 状态转移：explaining→awaiting_answer→（判分）→explaining 全链。
