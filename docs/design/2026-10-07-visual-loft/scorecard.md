评分依据：真实 Chromium 截图、录屏、`probes.json` 与 `metrics.json`。

- 作者：Claude Opus 5.5。独立复核者：另起的 Claude Opus 5.5，见 [review.md](review.md)。
- 评分对象：A 第二版（两轮修订后）、B、C。B、C 没有修订。
- 第一版 A 的原始截图在 `evidence/round-1/original/`（4 张，当时直接拍摄）。
- `?round=1` 只是**结构近似重建**：其中带有后续修复，见 `evidence/round-1/reconstructed/`，不能替代原始记录。

**刻度**：

- 5 = 桌面与手机都满足；
- 4 = 满足，但有一处已记录的弱点；
- 3 = 只在一种设备上满足；
- 2 = 部分满足；
- 1 = 不满足。

“复用成本”一项，分数越高表示成本越低。

## 4. 实测指标

测量环境：Headless Chromium 151.0.7922.34，Apple silicon，本地 fixture。

- 每格运行 3 次，取中位数，最大值另列。
- `cpuThrottle 4` 作为低端机的代理。
- 脚本：`prototype/capture.mjs metrics`。原始数据在 `evidence/metrics.json`，包含每次运行与每个交互窗口的帧间隔。

两个指标的算法：

- **INP 代理值**：本次操作序列中各交互的事件时长（按 interactionId 合并）取最大值。
- **帧间隔**：交互后 600ms 内，相邻两次 rAF 的最大间隔。

| 变体 | 设备 | CPU | CLS（最大） | INP 代理 中位 / 最大 | 空闲基线帧间隔 | 切屏帧间隔 | 插入步骤帧间隔 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A | 桌面 | 1× | 0.0003 | 64 / 72 ms | 27 ms | 53 ms | 35 ms |
| A | 手机 | 1× | 0.0021 | 80 / 120 ms | 26 ms | 38 ms | 48 ms |
| B | 桌面 | 1× | 0.013 | 56 / 80 ms | 27 ms | 53 ms | 43 ms |
| B | 手机 | 1× | 0.002 | 56 / 56 ms | 26 ms | 38 ms | 37 ms |
| C | 桌面 | 1× | 0.0005 | 56 / 72 ms | 26 ms | 86 ms | 43 ms |
| C | 手机 | 1× | 0.0016 | 48 / 48 ms | 26 ms | 34 ms | 43 ms |
| A | 桌面 | 4× | 0.0003 | 120 / 136 ms | 26 ms | 113 ms | 110 ms |
| A | 手机 | 4× | 0.0014 | 88 / 200 ms | 26 ms | 115 ms | 141 ms |
| B | 桌面 | 4× | 0.013 | 88 / 192 ms | 26 ms | 129 ms | 97 ms |
| B | 手机 | 4× | 0.0013 | 88 / 176 ms | 26 ms | 122 ms | 109 ms |
| C | 桌面 | 4× | 0.0005 | 72 / 88 ms | 26 ms | 109 ms | 89 ms |
| C | 手机 | 4× | 0.0009 | 80 / 88 ms | 26 ms | 89 ms | 90 ms |

判读：

- **CLS < 0.05：全部通过**（最大 0.013）。
  - 手机内联讲解在修复前曾达到 0.047，其中一次修复尝试使它升到 0.058。修复过程见 review.md §5 与决策 W6。
- **INP < 200ms：按 3 次中位数全部通过**（中位数最大 120ms）。
  - 单次运行的最差值为 200ms（A 手机，4×），正好落在门槛上，**不能宣称每次运行都满足**。
  - 运行间波动大：同一格在不同轮次间可以相差一倍以上。
- **“100ms 内反馈”**：1× 下各格中位数在 48–80ms，A 手机单次最大 120ms。
  4× 下中位数在 72–120ms。**未全部达成**，最慢的交互是切屏与插入步骤。
- **流畅（60fps）：未验证。**
  - headless 空闲时的帧间隔本身就约 27ms，不能用来证明 60fps（决策 M9 已给出有头浏览器或真机的测量协议）。
  - 4× 降速下，切屏与插入步骤出现 89–141ms 的长帧，这是确定的负面信号。
    对策：页内改用 FLIP（M3），公式等昂贵渲染前移到服务端或空闲时（M6）。
- `evidence/metrics-before-math-warmup.json` 是加入公式预热之前的单次测量，仅作对照保留。
- 指标只说明布局与交互本身的成本。生产中的数据加载、网络与服务端渲染，从 YUK-1354 起按真实路由测量。
- 三个变体之间的差异小于运行间的波动，**性能不构成选择理由**。
- 采集时机：本节指标在第二轮复核之前采集。之后只修正了三处换行与按钮尺寸（公式行距、“题干”按钮、1024 宽的快捷键提示），没有重新跑指标；截图、状态图、录屏与 probes 已在修正后重新采集。

## 5. 结论

选定方案：A 的首页、导航与视觉语言 + 三区同屏工作台。理由，以及不选 B、C 的原因，见[决策文档 §1](../2026-10-07-ui-visual-direction.md)。

以下几点已作为规则吸收：

- B 的同屏原则与手机标签栏（W2、N2）；
- C 的“停下与继续、建议同级可选”（H2）；
- C 的“关联须写明依据”（H8）。
