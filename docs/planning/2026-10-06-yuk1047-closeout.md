## 5. Current failures replenish bounded windows after correct regrades

Files:

- `src/kernel/read-models/failure-attempts.ts`
- `src/kernel/read-models/failure-attempts.current.db.test.ts`

Cause: `getCurrentFailureAttempts` forced `limit: null`, materialized all attempts, then removed currently correct legacy verdicts. Per-question quotas were consumed before that filter and could lose an entire question. Zero/negative limits still scanned history.

Fix: current-grade filtering occurs inside each active-row page before quotas are filled. The existing domain loader accepts this reporting mode. Flat scans use `(created_at, id)` keysets in either direction and at most `min(limit * 3, 300)` rows per query. Explicit full history, and existing unlimited reporting callers, use 300-row database pages. Per-question readers keep the existing SQL row-number partition windows, capped at 300 per question, and replenish them until filtered quotas are full or exhausted. Full event fields are returned by that query without the previous row cast. Raw `getFailureAttempts` retains original-failure history semantics.

Causal RED: all 5 new DB cases failed. Real postgres-js debug traces proved flat attempt queries had no LIMIT; the per-question query returned no current rows behind corrected heads; zero limit still queried history.

GREEN: 45 correctly regraded prefix rows, same timestamps, reverse physical insertion, subject-only appeal successors with supersede chains, two uneven question histories, forward public cursor continuation, explicit 325-row full history, zero/negative limits, `since`, and review opt-in. These are real Postgres queries and correction resolutions, not mocked database responses.

Actual database query boundaries, archived in `query-trace.jsonl`:

| Scenario | Result | Attempt scan queries | Bound |
| --- | --- | --- | --- |
| 45 corrected prefix + 20 retained, requested limit 2 | 2 correct retained IDs | 8 | Every LIMIT 6; continuation has strict created_at/id `<`; no OFFSET |
| A: 19 corrected + 7 retained; B: 2 corrected + 3 retained; per-question limit 2, global limit 1 | 2 per question, 4 unique IDs | 4 | Rank windows `(0,6]`, `(6,12]`, `(12,18]`, `(18,24]`; at most 6 payload rows/question/window |
| 23 retained + 8 corrected at one timestamp, ascending limit 5 | 5 + 5 + 5 + 5 + 3, then empty; all 23 IDs exactly once | 6 caller pages | Every LIMIT 15; public cursor continues from last returned ID |
| Explicit all history, 325 retained + 11 corrected | All 325, stable descending IDs | 2 | Every LIMIT 300 |
| Limit 0 / -1 | Empty | 0 / 0 | No event scan |

The related current-failure/legacy-queries/native-failure run passed 50 DB tests. Final query-log run passed the same 5 new cases and recorded the actual SQL/parameters to a caller-selected temporary path, respecting umask.

Limit: full-report result memory remains proportional to output size. The existing per-question rank query can scan/order matching history inside Postgres even though each returned window is bounded. This is a query-bound and correctness repair, not a query-plan or latency benchmark, and does not add a generic pagination framework or indexes.
