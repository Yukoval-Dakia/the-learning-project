## R1-P1-001: supply a libpq password for scratch TCP psql sessions

Primary location: `scripts/cutover-backup.ts:2267-2272`, especially the new `host: '127.0.0.1'` at line 2271. Supporting paths are `psqlArgs` at lines 1101-1116, scratch creation at lines 2243-2248, and readiness at lines 2275-2292.

The helper starts the normal PostgreSQL 16 scratch image with `POSTGRES_PASSWORD=loom`, then sends scratch `psql` connections over TCP loopback. The generated argv is `docker exec -i <id> psql -U loom -d <db> -h 127.0.0.1 -X -qAt -v ON_ERROR_STOP=1 ...`. It supplies no `PGPASSWORD`, password file, or other libpq credential. `POSTGRES_PASSWORD` configures image initialization; libpq does not use it as the client password. The standard PG16/pgvector image authenticates TCP host connections with a password. Its trusted local Unix-socket path does not apply after adding `-h`.

On that supported image, every readiness attempt fails authentication. The loop exhausts and emits `readiness_failed` before TOC, SQL restore or inspection. This affects default network-none, retained-loopback and SQL-only restore modes. It remains fail-closed, but prevents the advertised restore and parity-to-reopen path from working. The existing fake transport returns success for `select 1` unconditionally at `scripts/cutover-backup.test.ts:730`, so its successful receipts do not test this assumption. The canonical DB suite connects through its separate postgres-js client and does not run the helper's scratch connection path.

Contract: `docs/planning/2026-10-09-yuk1359-restore-reopen-integration-design.md:28-30` requires the selected scratch database and existing loom user/password to support actual restore/inspection and real identity observations. The coherence contract at `docs/planning/2026-10-09-yuk1359-restore-coherence-design.md:75` requires restoring and inspecting a compatible isolated scratch before comparison.

Reproduction for the parent, **not executed by this reviewer**: run the single already authorized full-parity helper invocation with valid sealed artifacts and the standard local PG16 image. On its exact owned scratch, the emitted read-only readiness command is:

```text
docker exec -i <owned-id> psql -U loom -d <selected-db> -h 127.0.0.1 -X -qAt -v ON_ERROR_STOP=1 -c 'select 1'
```

Under normal image host authentication this fails with no password supplied; the helper ultimately emits a failed receipt. Supplying `-e PGPASSWORD=loom` to that same container exec is a read-only diagnostic for the missing credential. No second restore, worker restart or authentication weakening is needed. Supply the known scratch credential for every TCP psql session, retain the TCP check that avoids the temporary initdb server, and verify the existing real helper path under parent ownership.
