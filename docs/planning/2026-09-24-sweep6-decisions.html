决策 1 YUK-1040 待裁决

seed 根节点的 θ̂/mastery 污染怎么堵

这是什么

系统里有一类「合成科目根节点」(如 seed:math:root):它是知识结构的锚点,不是真实知识点。上一轮已经修好 FSRS 复习卡这一侧 —— 不再给锚点建卡(YUK-1037)—— 但还留了两处尾巴:

  • θ̂ 能力值轴:答题结算时,settleSoloReview / settlePaperSlotReview 会把 referencedKnowledgeIds 直接喂给 θ̂ 更新,没有过滤 seed:*:root。生产目前还没有产生污染行,但 4 道绑在 seed:math:root 上的题一旦被作答,θ̂ 就会写到锚点上。
  • 存量数据:库里已有一行锚点的 FSRS 状态,另有 4 道只绑了锚点的 active 题。这些怎么处置需要您定,底线是不直接改 SQL。

选项对比

在 θ̂ 更新入口直接滤掉 seed:*:root,与 FSRS 侧同一手法。

特点简单直接;锚点彻底不进 mastery。

A2

沿用 FSRS 侧口径

混合绑定只写真实 KC;纯 root 绑定不写 KC 行。

特点语义更一致;但行为更复杂。

影响与代价

  • 现状不处理:4 道题一旦被作答,θ̂ 就会写到锚点上 —— 能力值轴开始积累污染,而锚点本不该有能力值。
  • A1 只加一个过滤点,口径一句话能说清;A2 与 FSRS 侧语义完全一致,但判断逻辑更绕、行为更难解释。
  • B 部分:a) 零动作零风险;b) 最彻底,但会 archive 锚点,且并入(into)目标必须选对;c) 需要您亲手跑一次性脚本。
  • 无论选哪条,都不直接改 SQL:要么走提案(propose→accept / knowledge-merge),要么走您执行的 ops 脚本。

建议

  • θ̂ 轴选 A1:改动最小,口径也最清楚 —— 锚点不是知识点,本就不该进 mastery。
  • 存量 FSRS 行先选 a)(惰性行 + 守卫兜底,零动作);若想彻底清理,再批准 b),into 目标由您确认。
  • 4 道 active 题走 propose→accept 正道补绑真实 KC。
  • coarse fallback 不急;若本次不裁决,默认保持现状。

决策 2 YUK-1038 已演进

unit_dimension 判分契约的生产链缺口

这是什么

物理题的「数值 + 单位」判分路由(unit_dimension)要求题目 metadata 携带一组契约对:reference_value:number + reference_unit:string。

上一轮已把路由触发改成「认这个契约」(YUK-1036)。但 Codex review 发现:生成链路根本产不出这个契约 —— QuestionAuthorDraft 和 QuizGenQuestion 的输出 schema 里没有这些字段,insert 时也不写。

后果:unit_dimension 在生成链路上实际不可达。注意,这不是误路由,而是死判分被正确避开 —— 系统没有出错,只是这个功能等于不存在。

OWNER 后续已演进 · 终态见新规划文档2026-09-24 演进

判分三层架构:Jev 廉价首选层 + LLM 保底层(已被取代)

取代说明:owner 随后裁定「不分批了,要上就全量迁移,支持任意题目」——本卡片的三层架构升级为五层问题/评估模型 + 全量迁移 + 一次统一切换。终态以 docs/planning/2026-09-24-question-assessment-redesign.md、2026-09-24-question-assessment-implementation-grounding.md、2026-09-24-question-assessment-decisions.md(D1–D19)为准;本节保留为决策历史。

三层架构

1

选择题(有 choices_md)→ exact 不变

字母 / 文本解析成 choice index,按集合相等判;单选多选都支持,多选必须全对(无部分分)。

2

非选择题 → 录入时由 LLM 声明判分层(二选一)

jev~$0.0004/次 · ~0.3s

Jev 决策模型快速判分,返回校准置信度。

适合答案理解难度低的题:数学填空、短答案、事实性问答。

llm现有 semantic judge

高级判分。

适合答案理解难度高的题:语文阅读理解、论述、需要推理链的题。

3

分类依据 = 答案的理解难度(录入 LLM 判断)

例:「语文阅读理解 → llm」「数学填空题 → jev」。

降级链(owner 拍死)

Jev 不可用(超时 / 故障)→自动降级 LLM 判分
Jev 返回低置信→自动升级 LLM 判分

Jev 是廉价首选层,LLM 是保底层 —— 不存在「Jev 挂了就没法判」的路径。

连带影响

  • unit_dimension / steps / keyword 三条路由的角色待定:可整体退役(Jev Choice 可覆盖六档信号),或降级为 Jev 内部实现细节 —— 实施时再定,不阻塞本设计。
  • 现有 judge_kind_override 枚举(exact / keyword / semantic)需扩为 jev / llm,或新增 judge_tier 字段;存量题的旧值映射(keyword→jev?semantic→llm?)属实施细节。
  • 生成 schema(QuizGenQuestion / QuestionAuthorDraft)需加判分层声明字段 —— 这是 YUK-1038 契约缺口的替代方案,原「schema 加 reference_value / reference_unit」选项被本设计取代。

决策 3 YUK-774 待批准

夜间任务编排「今晚图」

这是什么

夜间 DAG orchestrator(YUK-758)已经会把每夜运行态落库:dag_orchestration_run + dag_orchestration_node 两张表,逐节点记录 pending / enqueued / running / succeeded / failed / skipped 六种状态,外加详情和 stale 标记。

但目前没有任何读面 —— 数据在库里,看不见。要把数据读出来,票内规划了两条腿:

  1. admin observability 读端点:GET /api/admin/orchestration/runs(运行列表)+ /runs/[id](逐节点明细)。
  2. 「今晚图」可视化 UI:在 admin jobs 面展示当夜 DAG —— 节点状态 + 边 + skipped 原因。

票内两条硬要求:① 端点不能裸奔,必须与 UI 或消费者同波上线;② UI 须先走 design pre-flight(引用 design doc、声明组件类型、列文件清单)。

选项对比

批准建议

启动,端点 + UI 同波

按票内流程推进:design pre-flight → 单 PR 内读端点与「今晚图」UI 同波上线。

影响一次 design pre-flight + 一个 PR;之后每晚编排状态可视。

暂缓

不做读面,继续落库

不做读端点也不做 UI,运行态继续只躺在两张表里。

影响零开发成本;夜间编排继续是黑盒,出问题只能手工查库。

影响与代价

  • 只做端点、不做 UI 不合规:票内明确要求端点必须与 UI 或消费者同波上线。
  • UI 不过 design pre-flight 不能动工。
  • 两腿同波落地后,每晚 DAG 的节点态、边、skipped 原因都能直接在 admin 面看到。

建议

批准启动;UI 形态建议 admin 页内嵌「今晚 DAG」卡片/视图(与票内建议一致)。
