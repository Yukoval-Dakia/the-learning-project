## 2. Linearization decision and exact interleavings

The existing idle selector computes `MAX(event.created_at)` for actor user, falling back to started_at, strictly `< tick minus 5 minutes` (`src/server/boss/handlers/promote_conversation_idle.ts:29-46`). `idleConversation` later takes C + session FOR UPDATE and checks only active status (`conversation.ts:413-447`). No existing conditional update, queue lock, learning lock or event insert lock joins those operations correctly.

1. After selection: idle selects old user clock; chat's C transaction touches/resumes and commits; its Q transaction commits a fresh ask; idle takes C + row and still sees active, then writes idle. This is a source-permitted schedule, not a reproduced failure.
2. During transaction: even after adding a SELECT MAX under the idle row lock, Q or accept-chip can insert/commit after that SELECT because it never locks the session row. A conditional UPDATE with an event subquery also uses a statement snapshot and does not by itself protect against this phantom insert. Row status/version CAS can catch a prior resume but cannot see an insert-only writer.
3. The two-transaction chat gap is distinct: find/resume commits; idle wins; acceptance then commits an ask without another resume. A shared insert lock orders the commits but does not by itself repair the resulting idle status. Acceptance must recheck/resume in its own transaction through Conversation.
4. ABA: T1 freezes active version 7; another tick idles to 8; a resume restores active at 9. T1 must skip version mismatch even if the last user event did not change. If T1 already committed an idle receipt, replay returns that receipt without inspecting active status and without another transition. Different ticks admitted at version 7 also lose after the first transition.
5. Precision: at cutoff `12:00:00.000000+00`, `11:59:59.999999+00` is old; equal and `12:00:00.000001+00` are not. Candidate event/start timestamps must stay PostgreSQL text and be compared as timestamptz in SQL. JavaScript Date round-trips lose microseconds. Event timestamps can tie or be backdated, so a latest-event ID alone is not a witness that no new user event committed.

### Smallest recommended shared-write changes, requiring parent ownership approval

Introduce one table-free transaction advisory lock A(sessionId), with a fixed namespace in new `src/db/conversation-activity-lock.ts`. It is coordination only, never a clock/counter or new event writer. Take it until COMMIT/ROLLBACK in precisely these existing writers:

- `cap/copilot/server/conversation-writes.ts`, `persistCopilotInputEvent`: for actor user, acquire A immediately after optional review binding and before `writeEvent`. Ensure the exported Db call opens a transaction and a Tx call stays in its caller transaction. Do not acquire A before review binding's locks. Preserve event IDs, actor, timestamp, payload, idempotency and retention behavior.
- `cap/copilot/server/durable-dispatch.ts`, `reserveCopilotDurableAcceptance`: acquire C before Q; retain I and the replay/conflict lookup. Only for a new acceptance, call a transaction-local `Conversation.assertAcceptingTurnsTx` before input capture, so terminal sessions reject and idle resumes atomically with the accepted ask/QUEUED/head job. Extract that Tx entry from the existing Conversation transition; the public wrapper keeps its behavior. A replay of an existing acceptance must not resume/touch a session. The earlier chat transaction may remain, preserving selection/reuse behavior; this closes its gap without holding a lock across route/network work.
- `cap/copilot/api/accept-chip.ts`: after the existing optional proposal acceptance, wrap the final strict active recheck and user-event insert in one short transaction. Add/use `Conversation.assertActiveTx` with C + row locking; then A; then insert. Keep strict no-resume semantics. If idle wins first, this final write returns conflict rather than recording a fresh accepted chip against an unchecked idle session. The existing proposal-committed/event-failed window remains explicit.
- `cap/practice/server/assessment/attempt.ts`, `recordFormalAttemptCapture`: after its existing attempt-ID lock and replay lookup, take A for non-null session_id immediately before insertion. Do not introduce resume, rewrite submitted_at, or wrap evaluation in the lock. This shared writer can receive a conversation ID even when the UI usually sends a review ID. The change overlaps a practice owner and requires post-judge source/ownership reconciliation.
- `src/server/session/conversation.ts`: extract the existing idle mutation into one private Tx writer, retaining status/version/updated_at and `conversation.idle` payload. Add `promoteIdleConversationTx(tx, frozenCandidate, tickAt, cutoff)` that takes C, session row, A, then performs a fresh READ COMMITTED statement to validate eligibility and invoke that same writer. Return typed promoted/skipped outcomes and transition job-event ID. The legacy idle wrapper remains supported through the same mutation; no second state writer.

Existing lock graph uses C = `hashtext('copilot:session-selection')`, Q = two-key `hashtext('copilot-session-queue'),hashtext(sessionId)`, L = `hashtext('learning-state:write')`. These are distinct. Existing paths are `C → Sconversation`, `C → revert identity → L → learning rows`, `Q → I → Sreview(SHARE) → review-answer identity → assessment group/issuance`, and `L → assessment rows → attempt identity → record → settlement`. Evidence: `conversation.ts:116-123,413-416`; `durable-dispatch.ts:237-254,325-329`; `cap/copilot/api/revert-checkpoint.ts:30-36,115-124`; `src/db/learning-state-lock.ts:6-11`; review/activation references above.

Proposed additions are `C → Q → I → Sconversation → review-binding locks → A` for fresh chat; `C → Sconversation → A` for idle/strict chip; `L → assessment rows → attempt identity → A` for activated capture, or `attempt identity → A` for record-only capture. Settlement may take further learning locks after A, but already owns L. Idle never requests L/Q/assessment locks. No path may acquire C after Q/L/A, or introduce A before review-binding locks. Do not put C into the generic event writer: learning writers would add L → C against revert's C → L. Do not use the session row as a new universal event lock without analyzing review-row/conversation-row inversions. No provider work is enclosed. Verify these orders with actual concurrent transactions later; this graph is a design obligation, not a deadlock-freedom runtime claim.

With A held, the writer-first schedule commits its event before idle's fresh recheck, which sees a changed activity witness and skips. If idle holds A first, insert waits until idle commits; chat then uses its C/Conversation acceptance boundary to resume before committing the new ask. Strict chip loses cleanly; formal capture preserves its existing no-resume semantics. A fresh formal event after the idle transition does not retroactively invalidate that earlier transition. Guaranteeing that every later event resumes would be a new product rule, excluded here.

## 3. Fixed tick, candidate and receipt contract

Use schedule `* * * * *`, `Asia/Shanghai`, as currently declared (`src/server/boss/handlers.ts:42-48`). Native identity is exactly `sched-promote_conversation_idle-${scheduledAt.toISOString()}`; use the scheduled instant, never execution-time Date.now. Legacy identity is `legacy:${job.id}`, with immutable first-admission clock and explicit `legacy-first-admission` provenance, not a fabricated original scheduled minute. Validate the pg-boss job's family. Repeated delivery of a tick never resamples its time or adds candidates.

Persist one immutable tick with backend/provenance, tick_at, SQL cutoff = tick_at minus 5 minutes, admission/fenced decision, contract version and a sorted unique candidate array selected in one statement. Each candidate stores sessionId, selectedVersion, selectedStartedAt text, userCount as decimal text, and a discriminated clock witness: `{kind:'user', eventId, createdAtText}` for the greatest `(created_at,id)` user event, or `{kind:'started', startedAtText}` when count is zero. MAX determines age; count guards tied/backdated inserts without treating dispatch_seq as commit order. Do not store raw user messages or another mutable last_activity column. This witness relies on the existing append-only event contract; restore/deletion is not an online idle operation.

Admission semantics must be explicit: this freezes the current state at the first committed admission, using the scheduled cutoff. It does not reconstruct a historical snapshot at scheduledAt. A resume that commits after this snapshot is rejected by version mismatch, including an uncommitted resume that the selector could not see. A delayed tick first admitted after a no-message resume can freeze its new active version and still find the original user clock old. Under the preserved clock that is eligible, just like a fresh later tick; it is not replay of an earlier admitted candidate. Do not use updated_at to claim otherwise: `findOrCreateCopilotConversation` samples now before its transaction/lock (`conversation.ts:321-324`), so even without clock skew it is not commit-order evidence. Reject a requirement that every tick scheduled before a resume must be suppressed as already satisfied; that stronger rule needs a separately authorized persistent commit-order/admission boundary. Recommendation is the existing first-committed-admission semantics with exact scheduled cutoff and frozen version, not a new resume clock. Parent must confirm this edge if its intended guarantee is stronger.

Per candidate, under control SHARE → tick advisory lock → saved tick/receipt → C → Sconversation → A: return any prior receipt first; otherwise require frozen membership, correct family/type, active status, identical version/started_at and unchanged userCount/latest-event witness, plus the exact old-clock predicate. Missing/terminal/already-idle, version-changed, activity-changed and not-old/post-tick are explicit skipped receipts; corrupt state/contract is a failure. Apply one Conversation idle transition and write its receipt atomically. Receipt stores outcome, from/to version and job-event ID when promoted. State + job_event remain domain truth; the receipt is immutable tick execution evidence, not another lifecycle projection. Do not infer success from current idle status or a retained `conversation.idle` event alone: events can be pruned and the session can resume.

Same tick replay returns its receipt even after resume. An unprocessed old candidate fails the version/activity guard. A later fresh tick can legitimately re-idle a resumed active session with no new user event if the original user clock is still older than five minutes. Changing that behavior to a resume-based grace period would violate this task's original clock. No catch-up/replay is allowed to manufacture a fresh tick identity.

On any admission/row COMMIT error, inspect the writable primary in a new READ COMMITTED transaction behind the same control/tick lock. This waits for the original transaction to finish before deciding. A validated receipt means committed; confirmed absence means not committed; inaccessible primary, lock timeout or unreadable evidence remains unknown and blocks success/drain. Do not count it skipped. Only confirmed rollback may become an immutable `deferred-known-failure` receipt, preserving later-minute recovery without retrying an ambiguous effect. Distinguish completed-with-deferred from complete. The existing precedent implements these branches at `src/server/durable/session-orphan-family.ts:346-393,459-540`.
