## Desired behavior and scope

Ordinary application tasks export task, model, tool, child-agent, and worker spans
when the API or worker process has `LMNR_PROJECT_API_KEY`. The integration is
optional: without a key, initialization does not import the SDK, and task/model
wrappers call their original callbacks directly. There is no new queue payload,
database schema, coding-agent extension, or demo service.

`src/server/ai/laminar-tracing.ts` owns initialization, application async context,
span creation, metadata filtering, model completion observation, and bounded
shutdown flush. Export errors are isolated from application errors. Each business
callback executes once; tracing cannot trigger a retry. Existing business retries,
durable settlement, cancellation, and hooks keep their original owners.

## Source and SDK decisions

The installed Laminar skill and its `references/instrumentation-typescript.md`
were read from the main checkout without modification. The public registry's
[latest package metadata](https://registry.npmjs.org/@lmnr-ai%2flmnr/latest)
resolved to **0.8.49** at implementation time. The dependency is pinned exactly.
SDK signatures and behavior were checked against the declaration and source files
in the [0.8.49 npm artifact](https://registry.npmjs.org/@lmnr-ai/lmnr/-/lmnr-0.8.49.tgz),
with the [official TypeScript SDK repository](https://github.com/lmnr-ai/lmnr-ts/tree/main/packages/lmnr)
as supporting documentation.

The integration uses the SDK's typed `initialize`, `startSpan`, serialized parent
context, attributes, status, `end`, and `flush` APIs. It does not use `observe` or
`withSpan`: the inspected SDK exception path records raw exceptions, which exceeds
this application's capture policy. Application `AsyncLocalStorage` supplies
parenting, while explicit serialized SDK context connects exported spans.

Initialization sets `instrumentModules: {}`, `inheritGlobalContext: false`, and
a 500 ms trace-export timeout. `LMNR_DEBUG`, `LMNR_TRACE_METADATA`, or
`LMNR_SPAN_CONTEXT` cause this integration to skip initialization because those SDK
settings can import context or capture data beyond the allowlist. This check runs
before importing the SDK and again immediately after import, before
`Laminar.initialize`. The SDK itself loads dotenv files during import. API and worker
startup initialize after existing environment loading. The common worker entry
covers both standalone and `RW_WORKER` modes, with idempotent initialization.

## Capture policy

Default exports contain only explicit metadata fields: task/run/parent/logical
IDs, task/tool/job names and tool-call IDs, batch count, provider/model,
execution/business outcome, durable settlement, execution flag, usage observation,
cost basis/reference, and aggregate usage reconciliation. Metadata strings must
match the bounded identifier alphabet; numeric metadata must be finite and
nonnegative. Unknown fields are ignored.

Without explicit development opt-in, prompts, messages/history and tool arguments/results
are not copied. Image data, raw reasoning/CoT, provider bindings, credentials, request
headers, SDK frames and arbitrary exception messages remain excluded in both modes. Error spans receive only a fixed
status and execution outcome. Tests use secret and CoT sentinels to check this.

An individual capability can set `RunTaskCtx.laminarContent` with a sanitized input
summary and a final-result summary projector. The capability owns sanitization;
the helper serializes only `{ summary }` and caps each summary at 4,000 characters.
The projector is skipped when tracing is disabled and cannot change the business
result when it fails. There is no global context-dump switch. See the example in
[README](../../README.md#optional-laminar-application-tracing).

## Outcomes and usage

Execution completion is distinct from business acceptance. Generic task attempts
retain `business_outcome=unassessed`; selected native assessment and Copilot owners
add their own existing verdicts. A partial collected stream is an execution error;
an aborted lifetime is cancelled. Durable settlement reflects the existing write
result, rather than the mere presence of a successful provider response.

Model usage reuses `pi-usage-evidence`: explicit provider zero is observed zero,
while absent usage stays unknown. Only `llm.call` leaves carry additive SDK token
and cost attributes. Costs are labeled `estimated` with a `pi-catalog` reference;
they are catalog estimates, not invoices. Task-attempt aggregate counts/cost are
separate reconciliation metadata, marked nonadditive and including child usage.
Do not sum these aggregates with model leaves. If cancellation ends a leaf before
terminal usage arrives, its usage remains unknown and it ends only once.

## Shutdown and bundles

API flush follows HTTP/runtime drain; worker flush follows pg-boss drain. Flush
waits at most 500 ms, handles synchronous failure and late rejection, and never
runs on a request/model/tool hot path. It is best effort; a hard process exit can
lose buffered spans. Existing shutdown deadlines and exit behavior remain intact.

Server and worker builds bundle the dependency, matching the existing container
runtime's dependency-copy policy. Current build output is approximately 40.7 MB
and 40.8 MB respectively. The migration build marks the SDK external and does not
bundle its implementation; its output is approximately 5.1 MB. No-key application
startup still skips executing the SDK import/initialization path.
