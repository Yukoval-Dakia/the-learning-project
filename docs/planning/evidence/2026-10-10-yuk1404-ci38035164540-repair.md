## Backend-loss cause and repair

postgres 3.4.9's `reserve()` wrapper retains its physical connection object.
Its query handler calls `c.execute()` directly. `closed()` sets that object's
socket to null, whereas reconnect is entered by the ordinary client queue.
A query through a stale reserved wrapper without first reconnecting the client
therefore schedules `nextWrite()` against null. The pending query does not settle
normally. An ownership witness or the shared lock helper's finally-unlock can
reach this path after backend termination.

An independent in-process EventEmitter protocol transport reproduces the exact
uncaught error with the actual installed driver and a stale unlock after close.
It opens no TCP/TLS socket, listener or database. The previous lifecycle invariant
primed a reconnect before stale cleanup, so it proved successor isolation but
missed this closed-socket case.

The dedicated execution client now observes its own `onclose`, preserving the
injected callback, and makes loss sticky. Its reserved handles reject subsequent
tagged/unsafe SQL and new reservations before driver execution. Stale release
does not return a dead or replaced slot to a queue; whole-client disposal still
owns cleanup. The shared helper's immutable `begin`/`savepoint` closures are
returned exactly as Proxy invariants require; their SQL uses the guarded handle.
The original runner pool, successor clients, PID/lock witnesses, atomic
publication and paid-result fences remain intact.

The existing successor lock/transaction assertions remain, and a new installed
driver invariant covers a closed slot without reconnect, SQL through an immutable
transaction closure, rejection without extra writes, and original-pool usability.
The first new fixture run timed out because it reserved an unprimed connection
outside the protocol fixture's supported startup path. That failed log is retained
at `/tmp/yuk1404-ci-unit-initial.log`; the fixture now primes its own connection
with a real driver query. No timeout was extended or sleep added.
