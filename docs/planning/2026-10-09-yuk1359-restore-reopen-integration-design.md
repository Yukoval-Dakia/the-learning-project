# YUK-1359 restore-to-reopen integration decision

## Recommendation

Extend the existing restore helper with an explicit, bounded scratch loopback mode. It still creates a new random owned PostgreSQL container, restores once, and runs its existing full inspector/comparator against that same database. Retain that exact container for the parent's DBOS inspection and reopen. Change the preparation driver to bind only source identity during source phases and bind the restored endpoint once, after a successful actual helper receipt. Keep the worker bundle unchanged.

Use two **proposed new options**, `--scratch-loopback-port=<1024..65535>` and `--scratch-database=test_fork_<digits>`, together with existing `--keep`. These options do not exist in the inspected implementation. They must be implemented, reviewed and sealed before any command using them runs. Default behavior remains a new `--network=none` container with database/user `loom`. No arbitrary target URL, container selection, reuse, volume attachment, restore-to-existing mode, relay, product server or new acceptance framework is needed.

The accepted coherence design's “no published service port” rule becomes the default plus this narrowly documented parent acceptance exception. Its snapshot, full parity, quiescence and failure requirements remain intact. A loopback address alone does not establish isolation or ownership; the parent must hold and evidence the maintenance boundary through prelaunch inspection and worker launch.

## Alternatives rejected

- Reopen a preprovisioned second restore while citing the helper scratch receipt: different target/data history, no exact parity-to-reopen binding.
- Add arbitrary `--target`, reuse an existing container, mount/copy an unreviewed live volume, or target main/private data: expands restore authority and loses bounded ownership.
- Keep network-none and add a host relay/SQL-over-exec adapter: changes transport and worker lifecycle substantially and introduces an unnecessary service.
- Run the worker inside the PG image: no established pinned Node/dependency execution environment there; copying/installing tools or changing worker packaging is a larger unverified change.
- Stop/recreate PG to add a published port after parity, or rename its database afterward: breaks the identity/maintenance interval and introduces storage handoff. The proposed port/name must exist at initial creation.
- Keep database `loom` and broadly relax the prep URL rules: one helper option fewer, but less explicit disposable protection. A receipt-specific `loom` exception could be sound with all the same identity gates; retaining the test-name constraint via a bounded database option is the clearer small change.
- Copy full parity logic into the prep, trust only fixture comparisons, trust `verified:true`, or supply witness constants: none establishes the required helper proof on the exact live target.
- Restart source to finish pending work and then back it up: destroys the required pending-at-capture condition.

No simpler alternative preserves the current host worker, unchanged default helper mode, one restored dataset and exact target binding with fewer meaningful risks.
